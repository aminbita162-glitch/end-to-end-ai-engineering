04 — EVIDENCE MODEL AND CLAIM CLASSIFICATION
======================================================================
For each claim assign one observation class:
OBSERVED — directly inspected source, metadata, or artifact.
REPORTED — assertion made by source author or documentation.
INFERRED — reasoned technical interpretation, not direct proof.
NOT TESTED — test not executed.
BLOCKED — access, environment, rights, budget, or permissions prevent check.
FAILED — an executed, properly scoped check failed.

Separately assign outcome:
PASS / CONDITIONAL / FAIL / BLOCKED / NOT TESTED / NOT APPLICABLE.
Never collapse categories. A present test file is OBSERVED, but test success
is NOT TESTED until its execution is independently supported.

REQUIRED EVIDENCE FIELDS:
evidence_id, project_id, claim_id, source_url, source_commit_sha,
source_path, source_line_range_or_permalink, artifact_kind,
observed_at_utc, observation_class, result_status, method,
tool_version_if_used, source_run_url_if_applicable,
raw_artifact_hash_if_available, limitations, confidence,
independence_level, sensitivity, reviewer, follow_up.

Use explicit UNKNOWN / NOT VERIFIED instead of blanks suggesting success.
Pin full SHAs where available. For a changing website, include capture
timestamp and limitations; never pretend a website has a Git SHA.
Link to public artifacts instead of copying logs containing secrets or PII.
Do not claim external independent review when only a self-review exists.

EVIDENCE STRENGTH:
E0 unsubstantiated claim.
E1 source document or README statement.
E2 directly inspected code/configuration/release artifact.
E3 linked execution output with SHA, environment, command, and result.
E4 independent clean-environment reproduction.
E5 approved longitudinal operational measurement with provenance.
Evidence strength is not a quality score and is not automatically PASS.

13 — FORMAL PHASE CONTRACTS / STATE MACHINE
======================================================================
Each authorized phase is a finite transaction with states:
UNAUTHORIZED -> AUTHORIZED -> BASELINED -> PLANNED -> FILTERED ->
EXECUTING -> VALIDATING -> REPORTED -> AWAITING_OWNER.
Alternative terminal states: BLOCKED, FAILED, CANCELLED.
No transition from AWAITING_OWNER to another phase without a fresh owner
instruction. A failure must never be relabeled success for convenience.

Every phase execution requires the following contract:
- PHASE_ID and exact owner instruction / approval reference.
- Objective and falsifiable engineering outcome.
- Authorized repository, branch, allowlisted paths, and action classes.
- Explicit prohibited paths, services, commands, and side effects.
- Read-only source inventory and evidence inputs with SHA/date.
- Dependencies and preconditions, including clean working tree.
- Planned change units, each with reason, minimal files, and risk.
- Acceptance criteria, checks, expected artifacts, and stop triggers.
- Rollback/recovery approach that does not overwrite owner changes.
- Evidence provenance and redaction requirements.
- Commit permission and push permission as separate booleans.
- End-of-phase report and required next owner decision.

PHASE AUTHORIZATION IS NOT TRANSITIVE. Authorization for Phase 3 on IBM
is not authorization for Phase 3 on AILORA. Authorization to inspect a
public URL is not authorization to probe its APIs. Authorization to copy
public source is not proof that its license permits republication.

If an authorized phase depends on a missing fact: investigate only using
read-only paths explicitly in scope; if unresolved, mark BLOCKED and STOP.
Do not invent a workaround, branch, API credential, or replacement dataset.

EVD-<PRJ>-NNN for evidence; GAP-<PRJ>-NNN for unresolved gaps;
ADR-<PRJ>-NNN for engineering decisions. Never recycle an ID to mean
something different. If an item is superseded, preserve the link to its
replacement and the supersession date.

Evidence records must distinguish:
- ORIGINAL SOURCE: canonical repository and immutable SHA permalink.
- ORIGINAL EXECUTION: actual CI/test/benchmark run with timestamp.
- PORTFOLIO OBSERVATION: analyst's read-only inspection of that source.
- INDEPENDENT REPRODUCTION: third party reran it in separate environment.
- OPERATIONAL EVIDENCE: approved measured telemetry, with time window.

No evidence laundering: a copied log, generated chart, authored evaluation,
or repeated assertion does not become independent proof by being stored in
another folder. Derived material must point back to the original artifact.
If the source cannot be made public safely, use a sanitized metadata record
and state the independent verification limitation.

Hash only actual bytes available to the reviewer. Never invent a hash or
pretend that a Git blob SHA is interchangeable with a SHA-256 file digest.

warning. For release artifacts, preserve artifact identity, tag, and SHA.

15 — ARCHITECTURE DEPTH / SENIOR ENGINEERING CASE STANDARD
======================================================================
A high-quality case must explain not merely WHAT was built but WHY its
architecture was chosen, WHAT alternatives were rejected, WHAT can fail,
WHAT was measured, and WHAT remains unproven.

For each in-scope case, extract and verify when source permits:
A. Context and measurable problem, users, constraints, non-goals.
B. System context: clients, actors, external providers, data stores.
C. Container/component decomposition, responsibilities, interfaces.
D. Critical request/agent sequence, side effects, failure boundaries.
E. Trust boundaries, assets, identities, authorization decision points.
F. Data lifecycle: collection, validation, persistence, retention, deletion.
G. Consistency/concurrency: transaction boundaries, retries, idempotency.
H. Model architecture: deterministic vs LLM behavior, routing and fallback.
I. Deployment topology and revision mapping, without invented runtime proof.
J. Observability: logs, metrics, traces, alert ownership, missing coverage.
K. Threat model and domain-specific safety invariants.
L. Test pyramid, fixtures, CI enforcement, negative and failure tests.
M. Performance/cost hypotheses vs reproducibly measured outcomes.
N. Trade-off analysis: 2+ credible alternatives where source supports it.
O. Decision records: context, decision, alternatives, consequences, status.
P. Known limitations, operational risks, next evidence required.

Use C4-inspired context/container/component views or precise Mermaid only

Decision record minimum:
ADR_ID | source SHA | problem | constraints | selected approach |
alternatives | trade-offs | failure implications | evidence | status.

do not fabricate historical deliberation by the author.

16 — CRITICAL-PATH AND ADVERSARIAL REVIEW MODEL
======================================================================
For each project, choose a SMALL number of high-risk flows based on actual
source, not an arbitrary quota. For each flow record:
entry point -> trust boundary -> validation -> authorization -> state
transition -> external effect -> audit event -> recovery path.

Analyze the failure envelope: malformed input, partial failure, timeout,
retry, duplicate event, concurrency, stale state, policy unavailability,
third-party outage, and malicious retrieved content where applicable.
Document whether the source ENFORCES, TESTS, DOCUMENTS, or merely INTENDS
an invariant. Those four words are not interchangeable.

Financial agents: a deterministic risk-control rejection path is more
important than a polished dashboard. No trading or exchange interaction.
Document stale-price handling, exposure caps, replay, order duplication,
kill switch, and simulation bias only to the extent source supports them.

Multi-agent systems: map proposal, authorization, exact-action binding,
execution, audit, revocation, expiry, and replay. Identify any gap between
human approval in the UI and enforced backend/tool policy.

SaaS: map tenant identity, data ownership, cross-tenant reads/writes,
secret scoping, and billing assertions; do not infer isolation from a
framework choice or the existence of login pages.

Educational/technical-review content: map source claims, dates,
methodology, original contribution, confidentiality, and non-accreditation.

The portfolio may document a TEST PLAN for missing controls but MUST NOT
claim the plan was run. Never trigger security probes or runtime tests in
source projects or production endpoints under this directive.

17 — REPRODUCIBILITY AND INDEPENDENCE LADDER
======================================================================
Separate levels of proof:
R0 Statement only; no source artifact.
R1 Source and configuration inspected at immutable revision.
R2 Test/CI run artifact linked and associated with that revision.
R3 Build/test reproduction independently executed in isolated environment.
R4 Critical negative/failure cases independently reproduced.
R5 Operational behavior measured over a disclosed representative window.

These are evidence maturity levels, not a single composite quality score.
Do not upgrade a case to R3/R4/R5 from R1/R2 without actual qualifying
external evidence. This portfolio program does not itself authorize the
execution needed for R3-R5 in source projects.

Independence must be labeled SELF-REVIEW, SECOND-AGENT REVIEW,
SEPARATE-ENGINEER REVIEW, or INDEPENDENT THIRD-PARTY REVIEW, with
reviewer conflicts and tool reuse disclosed. A second AI agent repeating
an assertion is not independent reproduction.

Where only source-level evidence is available, the portfolio should
publish a precise reproducibility recipe pointing to source docs and
preconditions, not a fictional successful reproduction.
